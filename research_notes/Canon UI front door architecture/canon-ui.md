# canon ui as the front door to the whole canon experience

## 1. What does the current UI actually implement, and where does it stop?

### Takeaway

The current UI is a small, server-rendered, local review-and-rule-editing application with unusually deliberate security and genuine shared command logic. It is a good foundation for a front door, but it currently exposes only a narrow part of canon: first run, document reading, questions, stewardship, resource sharing, counterfactuals, and record exchange still require another interface.

### Cited Findings

#### Scope and product-state caveats

- **Observed checkout, 2026-11-02:** this audit reads the working tree, including the extensive pre-existing uncommitted institution implementation and documentation. It is not an audit of a clean release or of HEAD alone. Initial and closing tracked diff summaries agreed at 18 changed tracked files, 183 insertions/325 deletions; the new institution crate, examples, and docs were also already untracked. Only this research note was authored by this research session. Product/release claims must therefore distinguish working implementation from installed releases. The intended compatibility boundary is explicit in [docs/INSTITUTION_BOUNDARY.md:3–34](../../docs/INSTITUTION_BOUNDARY.md#L3-L34).
- **Observed code, critical:** UI `load` calls `canon_institution::legacy(&log, Some(store::now()))`, as does ordinary CLI `cmds::load`; the adapter simply calls the existing `derive`/`derive_at`. This is **legacy interpretation at the current clock**, not `shared-assent-v2`. MCP list/open/why/check use the same adapter with `None`, preserving their existing last-verified-act-clock reading. The latter check also creates action attributes at wall time, so even “the MCP clock” is not one undifferentiated value. [ui.rs:614–618](../../crates/canon-cli/src/ui.rs#L614-L618), [cmds.rs:79–86](../../crates/canon-cli/src/cmds.rs#L79-L86), [canon-institution/src/lib.rs:19–23](../../crates/canon-institution/src/lib.rs#L19-L23), [mcp.rs:250–252,386–388,415–435,448–452](../../crates/canon-cli/src/mcp.rs#L250-L452), [check.rs:534–550](../../crates/canon-cli/src/check.rs#L534-L550).

Its result separately contains interpretation, clock, source/arrangements fingerprints, effects, admissions, projection, and pending births. The diagnostic binary accepts `--arrangements` or the older `--basis`, reads inputs, prints JSON, and has no write path. It is an experimental read-only interpretation preview, **not a production-wide mode, migration, institutional-adoption command, or second production CLI**. [temporal.rs:13–73,331–447](../../crates/canon-institution/src/temporal.rs#L13-L73), [temporal.rs:331–447](../../crates/canon-institution/src/temporal.rs#L331-L447), [canon-institution/src/main.rs:5–41](../../crates/canon-institution/src/main.rs#L5-L41), [crate README:13–35,66–83](../../crates/canon-institution/README.md#L13-L83), [docs/INSTITUTIONS.md:142–169](../../docs/INSTITUTIONS.md#L142-L169).

#### What the existing design gets right

- **One record, shared writes:** browser proposals/replacements call `cmds::propose`/`replace`; decisions use `review::decide → cmds::answer`; retraction/silence/lift use `write_as`. `write_as` timestamps, signs when bound, and appends rather than rewriting history. This is a real use-case seam, despite its placement in a CLI module. [ui.rs:413–568](../../crates/canon-cli/src/ui.rs#L413-L568), [cmds.rs:318–331,542–605,661–699](../../crates/canon-cli/src/cmds.rs#L318-L331), [review.rs:261–274](../../crates/canon-cli/src/review.rs#L261-L274).
- **The queue asks the interpreter rather than copying voting rules:** for each pending commitment/retraction/ratification, `review::queue` tries hypothetical approval/objection and asks whether standing would change. It excludes already-answered items, derives eligibility from actual record behavior, and sorts yours first/oldest first. The terminal and browser consume it. This avoids a frontend implementation of joint/threshold/consent/subsidiarity. [review.rs:136–259](../../crates/canon-cli/src/review.rs#L136-L259).
- **Review has substance:** cards show who/when/room, complete proposed wording, proposer reason, what approval still needs, source excerpt when available, and separate approve/object actions. An objection's reason is required both in HTML and shared command logic. Single-rule amendments are a word-level LCS diff; the diff falls back to whole old/new text above 40,000 word-pairs. [ui.rs:766–847,1142–1195](../../crates/canon-cli/src/ui.rs#L766-L847), [cmds.rs:674–699](../../crates/canon-cli/src/cmds.rs#L674-L699).
- **Provenance is already reusable:** browser history uses `explain::explain`, also used by CLI/MCP. It includes authorship, source label, introduction/retirement reasons, prior/replacing entries, pending repeal requirements, and accepted/dismissed contradictions with reasons and revisit dates. It is more than an activity feed. [ui.rs:1039–1119](../../crates/canon-cli/src/ui.rs#L1039-L1119), [explain.rs:245–488](../../crates/canon-cli/src/explain.rs#L245-L488), [cmds.rs:907–947](../../crates/canon-cli/src/cmds.rs#L907-L947).
- **Useful native accessibility/mobile foundations:** language/viewport metadata, real forms/buttons/labels, `details/summary`, `fieldset/legend` for keys, visible focus styling, alert/status roles on many messages, system fonts, dark mode, wrapping flex controls, a 42rem reading column, and a ≤30rem media adjustment. No JS hydration or custom keyboard widget is needed to operate these forms. These are observed affordances, **not a completed accessibility or mobile conformance audit**. [ui.rs:654–667,730–741,835–843,1013–1033,1199–1308](../../crates/canon-cli/src/ui.rs#L1199-L1308).

#### Concrete risks and missing application behavior

1. **Review is incomplete even within governance.** `queue` includes commitments, retractions, and ratification changes, but neither its `Kind` nor `standing` nor enumeration handles `pending_policies`. CLI `approve` can resolve these policy proposals, and write feedback explicitly directs people to approve them. A `governs: all` policy change can thus require a decision that the UI never offers. This gap is in the shared queue, not something a new sidebar alone can fix. [review.rs:35–45,84–97,158–219](../../crates/canon-cli/src/review.rs#L35-L219), [explain.rs:192–207](../../crates/canon-cli/src/explain.rs#L192-L207), [cmds.rs:104–113](../../crates/canon-cli/src/cmds.rs#L104-L113).
2. **History resolver has already drifted by surface.** CLI `why` uses `resolve_why`, which resolves any act in the log, including silence/grant/ratification/position/adoption. UI still uses `resolve_any`, which resolves commitments/questions only, before calling the broader explainer. `linked` turns every syntactically matching act ID into a `/why/` link regardless. A grant ID can therefore be rendered as a history link that 404s. A read-only socket probe reproduced this for `can-73fc0e52ac35`. [ui.rs:1049–1059,1121–1139](../../crates/canon-cli/src/ui.rs#L1049-L1139), [explain.rs:119–176,245–260](../../crates/canon-cli/src/explain.rs#L119-L176), [cmds.rs:912–917](../../crates/canon-cli/src/cmds.rs#L912-L917).
3. **Taking back your own pending proposal is missing.** UI replacement/retraction first requires an active commitment, and its change forms only appear on active-rule history. Pending items do not get a history/action link in the queue. CLI amendment/repeal resolve commitments or questions, and `undo` can target any log act; the product's recovery vocabulary is broader than the UI's. Also, after your first position, UI no longer offers you the proposal even while it remains pending, so changing that position requires another interface. [ui.rs:472–521,709–721,1094–1115](../../crates/canon-cli/src/ui.rs#L472-L521), [review.rs:231–255](../../crates/canon-cli/src/review.rs#L231-L255), [cmds.rs:950–1004,1075–1109](../../crates/canon-cli/src/cmds.rs#L950-L1109).
4. **A clean-looking home omits important record qualifications.** Home shows active rules, pending review items, identity status, and silences. It does not surface open questions, overdue work, `unverified`, `unattended`, `ungoverned`, dangling references, carried/uninterpreted annotation warnings, or chronology disorder. CLI `list` and bare `canon` explicitly report many of these. “Nothing is waiting on you” is a narrower claim than the whole product's attention queue. [ui.rs:622–747](../../crates/canon-cli/src/ui.rs#L622-L747), [cmds.rs:797–858,1112–1131](../../crates/canon-cli/src/cmds.rs#L797-L858), [status.rs:16–65](../../crates/canon-cli/src/status.rs#L16-L65).
5. **Source context is bounded, but not stable evidence.** `review::passage` canonicalizes within the directory containing `.canon`, refuses escaping paths, and returns at most twelve current file lines. It does not use the saved draft artifact, compare a content digest, show the selected candidate's exact quote, or explain whether failure means unavailable/changed/unresolvable. Sources can have been imported from elsewhere, from rendered JSON chat, stdin, or git; their short source labels are not necessarily paths relative to this directory. Consequently an excerpt can be unavailable or no longer the text that was reviewed. The root boundary is the entire record parent, not the original ingestion allowlist; for `~/.canon`, that means the home directory. [review.rs:276–298](../../crates/canon-cli/src/review.rs#L276-L298), [ui.rs:815–823](../../crates/canon-cli/src/ui.rs#L815-L823), [sources.rs:101–125,178–218](../../crates/canon-cli/src/sources.rs#L101-L218), [draft.rs:679–711,2350–2373](../../crates/canon-cli/src/draft.rs#L679-L711). The previously considered fingerprinted-source design is a **proposal**, not an implementation guarantee: [LOAD_TEST_DESIGN.md:91–103](../../docs/LOAD_TEST_DESIGN.md#L91-L103).
6. **Atomic append is not a transaction or concurrency contract.** `store::append` uses append mode and one newline-inclusive `write_all`; an existing 8-writer/40-append test checks record parseability. But scoped propose/replace performs two separately signed/timestamped appends: first the rule, then its `Scoped` act. A second append can fail after the first succeeded; another reader can observe the intermediate state; no shared lock/revision token binds the check to the write. UI uniformly formats helper errors as “Nothing was written.” That statement is not justified for a compound operation's partial failure. Each `write_as` independently obtains `store::now`, also important if an eventual v2 write adapter needs a single submission-time identity for the pair. [store.rs:190–208,317–355](../../crates/canon-cli/src/store.rs#L190-L208), [cmds.rs:324–330,544–604](../../crates/canon-cli/src/cmds.rs#L544-L604), [ui.rs:440–468,485–500](../../crates/canon-cli/src/ui.rs#L440-L500), compare [temporal.rs:107–126](../../crates/canon-institution/src/temporal.rs#L107-L126).
7. **Fresh checks reduce staleness, but do not eliminate races/retries.** `/decide` reloads the queue; `/replace` and `/retract` check current active state; `/lift` checks live silences. These checks are not atomic with append. There is no expected-record revision or per-operation idempotency identifier; a lost response/retry may be another act at a later second. Redirect-after-write avoids ordinary refresh resubmission, not concurrent double-submit or uncertain-result recovery. [ui.rs:413–437,472–521,546–568](../../crates/canon-cli/src/ui.rs#L413-L568), [cmds.rs:324–330](../../crates/canon-cli/src/cmds.rs#L324-L330), [log.rs:112–137](../../crates/canon-core/src/log.rs#L112-L137).
8. **Errors lose work and blur transport/domain status.** Most form validation/write errors re-render home or history rather than repopulating the submitted text/reason. Record read failures return an HTML error with HTTP 200. `/decide` converts a load error into an empty queue and a “not waiting on you” message. `cmds::took` treats a failed reread as `Applied`; a future generic result API should not inherit that fallback. Domain refusal, recorded-pending, recorded-effective, failed-to-read, and failed-to-write need distinct outcomes. [ui.rs:423–436,447–468,485–500,622–630,1040–1047](../../crates/canon-cli/src/ui.rs#L423-L500), [cmds.rs:228–244](../../crates/canon-cli/src/cmds.rs#L228-L244).
9. **Multiple clocks are hidden inside shared presentation.** UI state derivation, queue assessment, and outcome reread each take a fresh wall clock. `explain::explain` itself calls `store::now` for ratification of active commitments despite receiving a derived `Canon`. Simply adding an “as of” picker around the current renderer would not guarantee a consistently historical explanation. MCP `None` clocks are an existing explicit compatibility distinction, not something to silently correct while extracting common loaders. [ui.rs:614–633](../../crates/canon-cli/src/ui.rs#L614-L633), [review.rs:264–273](../../crates/canon-cli/src/review.rs#L264-L273), [explain.rs:298–307](../../crates/canon-cli/src/explain.rs#L298-L307), [INSTITUTION_BOUNDARY.md:245–266](../../docs/INSTITUTION_BOUNDARY.md#L245-L266).
10. **Scale and reading behavior need evidence.** Every home render computes the whole review queue and emits all your proposals and all active rules. Queue evaluation clones the verified base and rederives up to twice per pending item. A many-proposal import can make every refresh/write expensive, while full long-rule text makes one page unwieldy; rule paragraphs do not use the source block's `white-space:pre-wrap`. There is no measured latency bound or UI pagination, whereas MCP already bounds lists and switches to an area census above fifty live rules. [review.rs:221–258](../../crates/canon-cli/src/review.rs#L221-L258), [ui.rs:633–707,875–907,1237–1254](../../crates/canon-cli/src/ui.rs#L633-L707), [mcp.rs:264–366](../../crates/canon-cli/src/mcp.rs#L264-L366).

#### Security boundaries: strengths to preserve, constraints to acknowledge

- **Observed strong local door:** random token bootstrap → 303 to `/` → `canon_ui` cookie with `HttpOnly; SameSite=Strict; Path=/`; exact loopback/localhost host-and-port check; cookie required for reads; every POST checks form token plus Origin and Fetch Metadata when supplied. Headers set restrictive CSP (`default-src 'none'`, only inline styles, self forms, no frames/base), no-store, nosniff, and same-origin referrer policy. `esc` escapes all five HTML-sensitive characters. [ui.rs:133–145,214–230,290–390,1312–1334](../../crates/canon-cli/src/ui.rs#L214-L390).
- **Identity binding does not accept arbitrary file paths from a page.** It accepts only a currently offered fingerprint; shared binding code signs the key act and vouches for prior acts under that name. UI binds one offered key; CLI can bind additional backup keys in the initial binding. A name binds once. Touch-required signing asks in the terminal running the page, so it is not yet a fully browser-contained experience. [ui.rs:570–583,842–843,971–1033](../../crates/canon-cli/src/ui.rs#L570-L583), [identify.rs:273–355,366–436](../../crates/canon-cli/src/identify.rs#L273-L436).
- **Current listener is not remote collaboration.** It binds IPv4 loopback only, has no multi-user login/session authorization, and every write is as the process actor. Filesystem access, signed identities, and optional git witness supply different layers of trust. Adding LAN access, phone access, or hosted multi-user service is a product/security-boundary decision, not a deployment flag. [ui.rs:119–158,324–345](../../crates/canon-cli/src/ui.rs#L119-L158), [store.rs:217–252](../../crates/canon-cli/src/store.rs#L217-L252), [guard.rs:4–35](../../crates/canon-cli/src/guard.rs#L4-L35), [SECURITY.md:69–92,108–120](../../docs/SECURITY.md#L69-L120).
- **Custom server caveats, static findings:** read-request limits are nominal 16KiB headers/64KiB advertised body and read timeout; body parsing breaks on EOF and truncates without verifying that declared length arrived. Content type and transfer encoding are not validated. Threads have no admission bound. These are robustness concerns for a growing application, not a claim of a demonstrated remote exploit. [ui.rs:179–180,232–283,153–157](../../crates/canon-cli/src/ui.rs#L232-L283).
- **Inferred multi-window issue:** cookie name/path is fixed while each UI launch creates a different port/token; cookies are host/path-scoped rather than port-scoped. Two canon windows on the same hostname can overwrite each other's authentication cookie. This should be browser-tested before proposing multiple simultaneous record windows; it is not solved by putting a record selector in the header. The relevant server behavior is [ui.rs:115,125–145,307–328](../../crates/canon-cli/src/ui.rs#L307-L328).
- **A future script boundary is real:** today's CSP and security claim explicitly depend on no scripts. Introducing JavaScript, external assets, uploaded documents, model calls, file browsing, or URL-based imports changes the reviewed surface. Preserve escaping and local POST protections; cost and review each new access path. Model acquisition is already centralized in `model::client_for`, with local-by-default gating; API keys live in the environment and are redacted rather than configured or echoed. [ui.rs:214–230](../../crates/canon-cli/src/ui.rs#L214-L230), [model.rs:127–154,505–551](../../crates/canon-cli/src/model.rs#L127-L154), [config.rs:68–109,154–172](../../crates/canon-cli/src/config.rs#L68-L172).

### Inferences

- **Highest risk is incomplete truth, not an old-fashioned rendering technique.** A polished shell around the existing routes would still hide unanswered questions, qualifications on authority, pending policy decisions, and recovery actions. Prioritize a trustworthy read/attention model and complete action lifecycle before animation or a command palette. This follows from the home/CLI contrast and queue/resolver drift above.
- **A new frontend framework is not required by current evidence.** Native HTML already handles the core review loop. Multiple task pages, bounded queries, typed application results, and optional small progressive enhancements can be assessed independently. A SPA is justified only by a measured interaction/lifecycle need and an explicit cost/security decision.
- **Treat successful appends and social adoption separately everywhere.** The page already tries to report “still waiting” versus “in force”; compound writes and hidden governance types make that separation more important as the UI expands. The v2 projection/admission split makes this a stronger future requirement, not permission to reinterpret ordinary UI now.
- **Distinguish private inquiry from public action.** A read-only `check` can reduce the exposure cost of asking; a question or objection becomes part of the record. A first-class UI should make both easy without silently recording exploratory thought or presenting absence as approval. Product rationale: [PRIMITIVES.md:829–883](../../docs/PRIMITIVES.md#L829-L883); actual read-vs-write split: [check.rs:553–621](../../crates/canon-cli/src/check.rs#L553-L621), [cmds.rs:1307–1332](../../crates/canon-cli/src/cmds.rs#L1307-L1332).

- No real-browser interaction, keyboard/screen-reader audit, contrast measurement, narrow-screen screenshot, user study, multi-window cookie reproduction, latency/load measurement, partial-write fault injection, or race reproduction was performed. Source affordances and inferred risks should not be reported as those results.
- The README says only the builders' group has used canon. No reliable evidence here establishes that another group's preferred first screen is the review queue, or that household workflows should dominate personal/code workflows. [README.md:3–18](../../README.md#L3-L18).
- Long-lived remote/browser-only use is an open product requirement. Current localhost/terminal/key-touch design does not answer it. “Mobile responsive” and “reachable from a phone” are separate questions.

## 2. What should people be able to accomplish, and what belongs in a shared application layer?

### Takeaway

The front door should orient a person in a particular record, explain what needs their attention, and let them follow a complete task from evidence to proposal to outcome and recovery. Build a small common application layer out of the existing shared seams; do not drive browser workflows by copying the CLI dispatcher or turning every verb into a button.

### Cited Findings

- **Product intent spans more than rule browsing:** find agreements in old notes/chat, retain reasons for changes, decide who has a say, keep questions and deliberate silences, and replay alternative policies. [README.md:3–21,63–85](../../README.md#L3-L21), [GUIDE.md:24–54](../../docs/GUIDE.md#L24-L54). Code/fixtures instantiate this broader scope: the Fernwood scenario covers boundary queries, a policy change, agent work, lapsed standing, escalated decisions, carried contradiction, sortition, and rule ratification. These are executable product examples, not evidence of widespread adoption. [fixtures/fernwood-commons/scenario.jsonl:6–114](../../fixtures/fernwood-commons/scenario.jsonl#L6-L114).
- **There are two different reviews.** `draft::review` accepts/edits/rejects/skips source candidates and writes assert/question/silence; it consults local `seen` state. `review::queue` handles already-recorded proposals awaiting assent, writing actor positions. “Accept this reading” and “Approve this proposal” can have different authority/effects and must not be flattened into a generic accept-all inbox. [draft.rs:1835–1850,2376–2502](../../crates/canon-cli/src/draft.rs#L2376-L2502), [review.rs:35–82,138–274](../../crates/canon-cli/src/review.rs#L138-L274).
- **Application state already extends beyond the log:** `.canon/seen`, `draft-runs/`, machine endpoint config, and lineage clones are local and intentionally ignored by git. The record remains shareable. Draft artifacts retain candidate quotes/chunks, partial checkpoints, resumed-review information, and model-run provenance; those are a better basis for import workflows than rerunning extraction on every browser visit. [store.rs:151–187](../../crates/canon-cli/src/store.rs#L151-L187), [draft.rs:1719–1850,1882–1894,2350–2373,2505–2519](../../crates/canon-cli/src/draft.rs#L1719-L1850).

These are module functions inside the binary, not a public reusable application library. [main.rs:11–47](../../crates/canon-cli/src/main.rs#L11-L47), [cmds.rs:318–331,544–699](../../crates/canon-cli/src/cmds.rs#L544-L699), [review.rs:138–274](../../crates/canon-cli/src/review.rs#L138-L274), [identify.rs:321–355,392–436](../../crates/canon-cli/src/identify.rs#L321-L355), [check.rs:94–150,495–523](../../crates/canon-cli/src/check.rs#L94-L150), [replay.rs:166–174,595–609](../../crates/canon-cli/src/replay.rs#L166-L174).
- **Why wrapping CLI dispatch is fragile:** handlers take string arrays, resolve ambient record/actor/time, print to stdout/stderr, and sometimes read stdin, launch tools, make network calls, write multiple files, or materialize a replay. MCP already constructs fake CLI flags to share check attribute parsing. Terminal draft review directly owns stdin; ordinary review is better separated through a `Prompt` adapter. A browser task needs structured results and explicit dependencies, not captured terminal prose or shell argument construction. [cli.rs:34–46](../../crates/canon-cli/src/cli.rs#L34-L46), [cmds.rs:70–86,301–330](../../crates/canon-cli/src/cmds.rs#L70-L86), [mcp.rs:415–435](../../crates/canon-cli/src/mcp.rs#L415-L435), [draft.rs:2381–2438](../../crates/canon-cli/src/draft.rs#L2381-L2438), [review.rs:314–321,478–495](../../crates/canon-cli/src/review.rs#L314-L321), [replay.rs:1204–1225](../../crates/canon-cli/src/replay.rs#L1204-L1225).
- **Boundary already decided:** pure mechanisms belong in core; explicit institutional admission/authority interpretation belongs in `canon-institution`; identity/time/storage adapters and presentation belong in the application. A new UI should not turn browser state, user-role heuristics, or a mutable core state object into institutional authority. [INSTITUTION_BOUNDARY.md:19–42,44–68](../../docs/INSTITUTION_BOUNDARY.md#L19-L68), [canon-institution/src/lib.rs:1–23](../../crates/canon-institution/src/lib.rs#L1-L23).
- **Voice is an architecture constraint:** limited attention; title by the job; plain task words; link depth; layer by audience. This argues for a task-first hub with explicit deeper paths, not one page containing the entire primitive/verb taxonomy. [VOICE.md:7–16,29–40,46–50](../../docs/VOICE.md#L7-L50).

Important interaction requirements:

- Show **what this action will record, as whom, in which record/room, and what assent it still needs**; after append, reread and show the actual outcome. “Propose” may take effect immediately for a seatholder under standing. A disabled control with an explanation can orient a person, but HTML disabling is never authorization.
- Let a person read **all** pending work and its provenance even when their vote is not needed; keep “waiting on you” as a focused default. There must be a route back to their own pending proposal, objection, or due item.
- Preserve exact source quote vs broader recorded context vs current-file excerpt as distinguishable evidence. Do not label a fresh file reread as the original quoted passage. Show unavailable evidence plainly.
- Read current people/procedures without entering edit mode; keep rule-making procedures separate from how operational actions are judged. Add expiry/consent clocks where they change the answer; avoid generic social “roles” that overstate the actual record's powers.

- Which cross-project patterns are actually small enough to transfer? This audit supplies evaluation criteria—explicit context, typed use cases, page/state lifecycle, stable IDs, bounded lists, accessible native interactions—not claims that a specific external project has solved them.

## 3. What is an affordable sequence, how should it be accepted, and what was actually verified?

### Takeaway

### Inferences

#### Ranked recommendation and rough cost envelope

The following are **planning estimates, not measured patches or approved cap increases**. They estimate gross added product Rust before actual deletions, assume server-rendered pages, and exclude test lines. Extraction/relocation is separately identified. No proposed net growth fits today's one-line aggregate headroom without genuine cuts. The ranges should be replaced by a small actual diff and before/after inventory before authorizing each slice; they must not be summed as a committed roadmap.

| Rank | Recommendation / what it buys | Extraction and cost posture | A small acceptance check, when implemented |
|---|---|---|---|
| **1** | **Extract shared view/write context and truthful outcomes before expanding.** Resolve all explainable acts through the common resolver; make pending policy decisions and recorded-vs-effective outcomes first-class; surface record qualifications. | Target a **net-neutral** extraction, mostly relocating existing `cmds`/`review`/`explain` code, with roughly 60–140 gross lines for missing cases/results. Cross-cutting small checks should attach to the slice that creates their need, not become a new test program now:

- **Concurrency/outcome:** inject failure between rule and room appends; result reports exactly what was recorded and recovery; two sessions cannot quietly apply a stale edit as though the viewed revision were current. Count source bytes/acts before and after. Reuse existing socket/temporary-record patterns.
- **Clock:** one consent decision changes after its deadline without any new act; the rendered state, required people, and explanation use the selected clock. Preserve the MCP legacy-clock distinction until separately approved.
- **Security boundary:** every added POST is tested for token/origin refusal and no write; a source path outside the intended root cannot be rendered; an unoffered key/path cannot bind; two locally open records do not invalidate each other's sessions or cross-write. If scripts are introduced, validate the revised CSP and escaping with actual browser behavior.
- **Accessibility/recovery:** keyboard-only navigation/form submission, labels/headings including history pages, focus/error announcement, user input retained after a validation error, 320px/200% text reading without lost controls, and measured light/dark text contrast. These are cheap focused checks, not a claim the current CSS passes them.
- **Cost:** record raw/product Rust, HTML/CSS/JS/TS size, production dependencies and lockfile changes, generated/bundled bytes, test changes, and net deletions for every frontend slice. No unmeasured shift of domain logic into JavaScript. Use the existing lean gate plus an explicit report before proposing a new frontend measurement policy.

#### How to evaluate lessons from svrngs / sovereign-desktop

Use the other researchers' concrete implementations to ask: does a pattern help a person keep the record/actor/interpretation/clock straight; keep application logic out of components/CLI parsing; preserve task state through long operations; bound large read models; retain provenance and errors; or make keyboard/mobile interaction reliable? Borrow a minimal component/service/lifecycle pattern only when it answers one of those needs here. A desktop shell, routing framework, global store, generated bridge, or UI kit should not be imported merely because it exists there. The current canon evidence supports **seams and lifecycle improvements first**, and does not yet select a frontend framework.
