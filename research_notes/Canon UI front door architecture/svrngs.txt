# svrngs frontend architecture: concrete lessons for canon’s front door

## 1. What frontend actually exists, at what revision, and under which boundaries?

### Takeaway

The most transferable implementation is **the embedded home page’s shared primitives, explicit state/effect boundary, and calls into the same Rust application services as the CLI**. ## 2. Which seven lessons transfer, and what should canon avoid?

### Takeaway

Borrow **specific ownership rules and failure handling**, not the whole framework or platform. Highest leverage: one Rust decision path, explicit per-workflow state, stale-answer protection, local feedback, and deep links carrying stable context. The examples below are observed implementations; canon applications and costs are provisional recommendations based on the supplied canon brief.

### Cited Findings

#### 1. Make the UI a peer caller of application services

**Observed responsibility:** home’s join route parses input and delegates to `at.host.join`; CLI’s `join_group` also calls `node.host().join`. The home’s group creation calls `Asking::found`; its router merges existing surface/removal/room/play routers instead of cloning their deciding inside JS. Phone joining uses `svrngs_core::joining` and `seed::answered`, not a second JS implementation of signing/seed belief. [home.rs:605–612,641–668,156–164](file:///Users/alexsbryan/dev/svrngs/crates/svrngs-node/src/home.rs#L605-L668); [cli.rs:1610–1638](file:///Users/alexsbryan/dev/svrngs/crates/svrngs/src/cli.rs#L1610-L1638); [web/src/join.rs:14–17,85–125](file:///Users/alexsbryan/dev/svrngs/web/src/join.rs#L14-L125).

**Why canon benefits — recommendation:** UI review/change/undo, approvals, draws, and rotations should ask the Rust application boundary for an answer and display the returned judgment/reasons. A browser reducer decides whether a drawer is open or a request is pending; it does not decide whether an agreement stands, a seat is authorized, or a resource allocation is valid. UI/CLI/MCP parity becomes reuse of one service path rather than reimplementation.

**Adoption cost:** medium if existing application calls are available, high if adapters currently own orchestration. Existing routes and extraction opportunities must be confirmed by the canon investigator. Prefer fewer, narrow, behavior-preserving adapters; near-zero Rust headroom makes parallel orchestration expensive. A generated client is optional: a tiny checked transport module plus representative contract fixtures can precede any generator.

**Failure modes/debt:** the observed handwritten client interprets response shapes in feature modules; JOIN destructures a positional result tuple. That is easy to drift without a generated/checked contract. The fetch helpers also discard most error metadata into `Error(message)`. Preserve useful status/domain identifiers in a canon client rather than copying these wrappers literally. [group.js:18–22](file:///Users/alexsbryan/dev/svrngs/crates/svrngs-node/src/home/page/group.js#L18-L22); [join.js:18–24](file:///Users/alexsbryan/dev/svrngs/crates/svrngs-node/src/home/page/join.js#L18-L24).

#### 2. Give each workflow one state owner and a visible effect boundary

**Observed responsibility:** `machine.js` separates pure `step(state,message)` from asynchronous `io`, validates named region states, notifies subscribers, and traces transitions/refusals. `useStore` subscribes and immediately rereads so an update between render and subscription is not missed. Phone composition rejects two flows claiming one field/region/message and rejects changes to another flow’s fields. [machine.js:12–47](file:///Users/alexsbryan/dev/svrngs/crates/svrngs-node/src/home/ui/machine.js#L12-L47); [view.js:14–31](file:///Users/alexsbryan/dev/svrngs/crates/svrngs-node/src/home/ui/view.js#L14-L31); [page.js:32–64](file:///Users/alexsbryan/dev/svrngs/web/page/page.js#L32-L64).

**Why canon benefits — recommendation:** put route/current-record identity in one shell owner, server snapshots in one record-scoped owner, and draft/form/disclosure state in the relevant workflow. An async draft answer must still belong to the record and draft revision that requested it. This gives review quotations, proposal editing, and approval work an understandable lifetime.

**Adoption cost:** low-to-medium for a small reducer and explicit effects; medium-to-high for the full runtime ownership/composition framework. No XState, Redux, global bus, or plugin registry is required to adopt the pattern.

**Failure modes/debt:** `get()` exposes state references; shallow copy/ownership checks are discipline aids, not deep immutability or static typing. Effects are scheduled in array order, but promises execute concurrently and can complete out of order. The runner has no cancellation/disposal API; unmounting the view only unsubscribes it. Canon should introduce cancellation/generation checks where context changes, not assume this runner supplies them. [machine.js:13,31–47](file:///Users/alexsbryan/dev/svrngs/crates/svrngs-node/src/home/ui/machine.js#L13-L47); [view.js:18–31](file:///Users/alexsbryan/dev/svrngs/crates/svrngs-node/src/home/ui/view.js#L18-L31).

#### 3. Treat async truth as part of the user experience

**Observed responsibility:** request counters reject late answers; GROUP reads independent data concurrently, allowing people to render before slow lends. HOME keeps content during `rereading`. Phone entry keeps its previous list and reports reread failure. SHELF disables conflicting input, prevents duplicate submit, says “Bringing…”, and rereads projections with bounded 1/2/4/8-second waits after an accepted command. [machine.js:18–22](file:///Users/alexsbryan/dev/svrngs/crates/svrngs-node/src/home/ui/machine.js#L18-L22); [group.js:28–50](file:///Users/alexsbryan/dev/svrngs/crates/svrngs-node/src/home/page/group.js#L28-L50); [home.js:25–31,49](file:///Users/alexsbryan/dev/svrngs/crates/svrngs-node/src/home/home.js#L25-L49); [enter.js:21–25,62–82](file:///Users/alexsbryan/dev/svrngs/web/page/enter.js#L21-L82); [ui/shelf.js:25–55](file:///Users/alexsbryan/dev/svrngs/crates/svrngs-node/src/home/ui/shelf.js#L25-L55).

**Why canon benefits — recommendation:** distinguish “reading”, “no agreements”, “could not read”, “previous answer; refreshing”, “draft generated”, and “change recorded”. Re-read affected Rust projections after a write and on returning to the tab so CLI/MCP changes appear. Model/source operations should keep the person’s input on failure and show phase text, not invented percentage completion. Render independent record/history/model-health information independently.

**Adoption cost:** low for request tokens, explicit states, refresh-after-write, and local status; medium for resilient long-running task observation. A first slice need not add a generalized job service.

**Failure modes/debt:** do not blindly retry writes after an ambiguous transport failure; the command may already have committed. Read/reconcile first unless the existing service provides safe request identity. SHELF’s polling follows svrngs’ delayed carried-file projection; canon should not import that polling if its local command already returns an authoritative projection. Retry exhaustion is traced rather than prominently surfaced in SHELF, so copy the boundedness, improve the explanation. [ui/shelf.js:33–39](file:///Users/alexsbryan/dev/svrngs/crates/svrngs-node/src/home/ui/shelf.js#L33-L39).

## 3. What minimum viable structure does this suggest for canon?

### Takeaway

**Recommended shape:** one embedded browser shell, one current-record/URL owner, a small Rust-facing client, a few shared semantic primitives, and workflow modules that render authoritative Rust answers. Keep typed input and disclosure state in the browser; keep durable governance, model execution/configuration, and service lifetime in Rust. This is an application of the observed embedded home/service reuse and explicit ownership pattern, not a claim that svrngs already implements canon’s desired UI. [home.rs:101–164,641–668](file:///Users/alexsbryan/dev/svrngs/crates/svrngs-node/src/home.rs#L101-L668); [machine.js:1–10](file:///Users/alexsbryan/dev/svrngs/crates/svrngs-node/src/home/ui/machine.js#L1-L10); [ARCH_PRINCIPLES §12](file:///Users/alexsbryan/dev/svrngs/docs/principles/ARCH_PRINCIPLES.md#L353-L375).

### Cited Findings

- Embedded asset serving, explicit feature composition, local state owners, shared native primitives, and refresh-after-write are all working-source patterns, with no dependency on adopting the phone networking stack. ### Inferences

#### Proposed responsibility map — provisional, names illustrative

```text
existing embedded UI assets/
  app.js          # one bootstrap; shell, navigation, record choice, URL/back/forward
  context.js      # current record + read generation + snapshot freshness
  client.js       # one checked HTTP boundary; preserve structured Rust errors
  state.js        # small transitions/effects only where async workflows need them
  ui.js           # actions/status/fields/disclosure/quotation/record references
  work.js         # first end-to-end review -> draft/change -> result/history slice
  [later workflow modules, only as justified by actual journeys]
```

This is a boundary sketch, not a demand for six new files or for a frontend rewrite. Combine modules if existing code already owns these jobs. Shared primitives may use existing DOM rendering; choose Preact only if component reuse and state subscriptions justify its vendor/update cost. All assets remain build-time inputs embedded by the single Rust binary, using the existing server/origin/session design.

**State policy:** the URL names record, workflow and stable target; shell context resolves it and owns its lifetime. Server answers carry the authoritative result/reasons and, if existing APIs support it, a revision/freshness marker. Pending work carries record ID and request generation. Per-workflow state owns form input, expanded explanation, pending/error/result. Reads refresh after relevant mutations and tab return; first implement a simple full-record refresh if cheap. Do not introduce an entity cache/invalidation graph without evidence of a performance problem. The motivating examples are HOME’s broad refresh, GROUP request counters, and the phone’s stale-list behavior. [home.js:25–31,62](file:///Users/alexsbryan/dev/svrngs/crates/svrngs-node/src/home/home.js#L25-L62); [group.js:30–37](file:///Users/alexsbryan/dev/svrngs/crates/svrngs-node/src/home/page/group.js#L30-L37); [enter.js:21–25,72–82](file:///Users/alexsbryan/dev/svrngs/web/page/enter.js#L21-L82).

**Navigation hypothesis to validate with the full canon brief:** organize around work rather than raw record CRUD: current agreements and what needs attention; review/source/draft/change; governance/people/seats/rooms/procedures/approvals; questions/tensions/revisit; shared resources/draws/rotations; history/sharing; model/setup. Preserve target context across these places, so a question can lead to a source, a proposal, an approval, and the resulting history. This is a recommendation based on the user-supplied workflows, not a taxonomy found in svrngs or a claim that all these screens are funded.

**First vertical slice:** open/select a record, follow a deep link to a review/source item, inspect its quotation and Rust explanation, request a draft with model identity visible, edit it, ask the existing application service to make the change, show the recorded result and history, and exercise existing undo semantics. Include a refused operation, a failed model request, and an externally changed record. If source/draft/change are not connected by current services, choose the nearest genuinely end-to-end supported journey first rather than building a parallel UI-specific domain pipeline.

#### Small acceptance bar before expanding scope

1. A fresh visitor can choose/open a record and start a useful supported workflow without CLI knowledge; empty/unchecked/refused states each offer the relevant next step.
2. A bookmark/reload/back/forward round-trip preserves record and target; an unavailable target is named rather than substituted.
3. Review/draft/commit/refusal/history show authoritative service outcomes; local drafts are visibly distinct from recorded changes.
4. An old async answer cannot repaint a newly selected record; duplicate submit and ambiguous write failure have explicit handling.
5. Returning after a CLI/MCP change refreshes the read model without erasing typed work.
6. Keyboard/focus/status behavior and a narrow viewport are exercised in a browser; pure state tests cover a late answer and failure recovery. Existing Rust contracts remain the oracle.
7. Report product JS/TS, HTML/CSS, Rust, tests/tooling, and vendor bytes separately. Expansion waits for a costed workflow decision.

These are recommended future acceptance criteria grounded in the transition/browser techniques above, **not checks run in this research session**. ### Gaps

- The exact minimum depends on the other canon investigation: which workflows are already exposed, where current-record selection lives, whether source/draft work has persistent job identity, how CLI/MCP mutations become observable, and how much JS/TS/Rust can be approved.
- A service/client schema-generation decision needs a real parity/maintenance cost comparison. svrngs demonstrates a small handwritten boundary, not evidence that hand-maintained schemas scale indefinitely.
