# Make canon’s UI carry whole journeys

For the small-release implementation sequence, start with
[Ship a UI people can use daily](../docs/UI_PLAN.md).

Status update: this report records the pre-implementation audit. Browser-first
setup and UI-1–4 have since been implemented in the working tree; the linked
execution plan records current verification and measured cost.

**Make the UI the place where a person can understand their group’s record, do something deliberate, and see what actually happened.** A first-class entry point connects opening a record, finding agreements in notes, reviewing evidence, proposing changes, participating in decisions, and recovering from mistakes; it is more than a browser version of the command list. Keep canon’s local-browser, single-binary delivery and authoritative Rust semantics, while borrowing bounded responsibility patterns from svrngs and the Commonwealth desktop client. **The first milestone should complete one trustworthy participant journey in an existing record: find a pending decision, inspect its evidence and authority, approve or object, and follow the actual outcome into working history.** Repair misleading outcomes and incomplete attention/history before adding broad new screens. Continue with server-rendered pages and native forms initially; reconsider a compiled frontend only after a source-review workflow demonstrates a concrete interaction need. All architecture, staging, and acceptance checks below are recommendations, not implementation approval.

## A first-class entry point finishes the person’s task

canon’s stated job is to find agreements in old notes and chat and preserve reasons when they change. Its product also includes authority, questions, intentional silences, shared resources, portable records, and alternative-policy replay. That breadth is real implementation scope, but not evidence that every household, code project, or individual wants the same home screen. The README says the only group using canon so far is its builders’ group. Treat the journeys below as hypotheses to test, rather than an established usage hierarchy ([README:3–21,63–85](../README.md#L3-L21); [executable Fernwood scenario:6–114](../fixtures/fernwood-commons/scenario.jsonl#L6-L114)).

The existing browser is a useful foundation. It launches for one resolved record and actor, serves native HTML without JavaScript, and shares proposal, replacement, decision, signing, and append logic with terminal workflows. Review cards already show wording, reasons, required assent, source excerpts, and amendment differences. However, its entire page surface is home, identity binding, and individual history, with seven POST actions. A missing first-run path is especially consequential: record resolution fails before the listener starts, so a newcomer cannot enter through the UI to create a record ([ui.rs:119–158,330–363](../crates/canon-cli/src/ui.rs#L119-L158); [review cards:766–847](../crates/canon-cli/src/ui.rs#L766-L847)).

### Two connected stories are better than a screen per verb

In the participant story, Sam opens the intended house record, sees the acting name and whether it can sign, and finds an agent’s proposed quiet-hours change. Sam reads the original passage, the changed wording, the responsible room, and exactly whose approval is required. Sam objects with a public reason, later returns through the same proposal/history link, and can revisit that position or withdraw Sam’s own pending work using existing permitted semantics. If the change becomes effective, history explains why; if signing, reading, or writing fails, the typed reason survives and the page identifies what, if anything, reached the record. This is a proposed legacy-compatible journey, not a claim that the optional institution-house example already operates in the ordinary browser.

In the steward story, Mira opens or deliberately creates a record with an appropriate profile and founding authority, selects a bounded set of meeting notes, checks where model requests will go, and starts extraction. Mira leaves the task, returns to the saved run, and reviews one candidate beside its exact quotation and recorded context. Accepting a reading records a proposal, question, or silence as appropriate; it is **not the same decision as assenting to an already-recorded proposal**. The journey continues through seats and procedures, unanswered questions/conflicts, a shared turn or draw when relevant, and export of the resulting record. Existing terminal candidate review makes these distinctions explicitly and stores rejection differently from skipping ([draft:2376–2502](../crates/canon-cli/src/draft.rs#L2376-L2502); [local application artifacts:151–187](../crates/canon-cli/src/store.rs#L151-L187)).

Use primary navigation for **For you**, **The record**, and **Ask or propose**. “For you” distinguishes assent from questions, due work, and record-health qualifications; it never equates an empty assent queue with a healthy record. “The record” provides find/filter, rooms, questions, silences, and contextual history. “Ask or propose” separates private inquiry from public acts. Show **Shared things** when relevant. Keep **People and how we decide** readable from every decision, with setup/import, sharing, tools, raw evidence, and advanced comparisons reached through contextual links. This is a progressive-disclosure hypothesis, not a commitment to seven tabs; it follows canon’s task-first, limited-attention voice ([VOICE:7–16,29–50](../docs/VOICE.md#L29-L50)).

## Keep record, actor, interpretation, and time separate

The shell must answer four independent questions. A record’s display name is not its identity, choosing an actor is not authenticating as that person, and choosing a presentation profile must not choose governance semantics.

| Context | Proposed explicit meaning | Mutation rule |
|---|---|---|
| **Selected record/group** | Resolved record handle/location and copy/lineage context; group name is a label. Deep links identify record and target. | Capture the target record for the operation. An unavailable bookmark must not fall back to another record. Browser paths are not arbitrary filesystem capabilities. |
| **Acting identity** | Full actor, resolution source, key-binding/contestation/signing availability; seats displayed separately. | Freeze actor and signing requirements at submission. Changing a displayed name does not grant authority or possession of a key. |
| **Interpretation** | Ordinary legacy reader, or a separately named/versioned experimental reading with retained arrangements and fingerprints. | Preview cannot supply authority for an ordinary write. Returning to ordinary work requires explicit context and revalidation. |
| **Evaluation clock** | The clock policy and captured instant used for a view/use case; historical views are read-only. | Expiry and consent can change answers without an append. Revalidate a current action at submission; an interpretation activation boundary is not the evaluation date. |

These are proposed application contracts grounded in current directory/actor resolution and interpretation code. Today UI and ordinary CLI read through `canon_institution::legacy` at wall time; MCP list/open/why/check preserve legacy reads using `None`, meaning the existing last-verified-act-clock behavior. MCP check also creates action attributes at wall time. **Reuse must preserve these distinctions before any deliberate clock migration.** The explanation path itself currently calls `store::now`, so adding an “as of” picker would not make it consistently historical ([UI loader:614–618](../crates/canon-cli/src/ui.rs#L614-L618); [CLI loader:79–86](../crates/canon-cli/src/cmds.rs#L79-L86); [MCP:250–252,386–388,415–452](../crates/canon-cli/src/mcp.rs#L415-L452); [explanation:298–307](../crates/canon-cli/src/explain.rs#L298-L307)).

Presentation profile is an additional, separate dimension. Personal commitments, code principles, and house rules share record concepts but not all output behavior: personal checks deliberately omit verdicts. Carry that protection through a shared result/presentation boundary instead of making profile a theme selector ([profile.rs:1–20,50–107](../crates/canon-cli/src/profile.rs#L1-L20); [check payloads:495–523](../crates/canon-cli/src/check.rs#L495-L523)).

Record writing/authentication, institutional assent, source evidence, and effect times answer different questions. A signature identifies the author under the record’s trust rules; it does not prove the group agreed. A quoted passage explains where a reading came from; it does not authorize adoption. An immutable act’s written time must remain intact when an interpretation assigns a later effective time. Witness information helps inspect record integrity, not certify social legitimacy ([boundary:204–226,262–266](../docs/INSTITUTION_BOUNDARY.md#L204-L226); [source/effective time explanation:94–107](../docs/INSTITUTIONS.md#L94-L107)).

Temporal v2 is currently a **source-built, experimental, read-only preview** selected by `--arrangements`, not a released UI setting. Its output separates projection, admissions, pending births, effective times, and source/arrangements fingerprints. The older `--basis` reader remains distinct. A future UI preview needs a visibly separate workspace, supported-profile checks, retained input identity, and a comparison to ordinary legacy results. Production adoption needs an explicitly designed and versioned choice: who agrees to the starting arrangements, how that agreement is retained/shared, how unsupported cases fail, and how existing records are migrated or reinterpreted. A toggle that quietly changes existing meanings is insufficient ([temporal types:13–73](../crates/canon-institution/src/temporal.rs#L13-L73); [runner:5–41](../crates/canon-institution/src/main.rs#L5-L41); [limits:245–266](../docs/INSTITUTION_BOUNDARY.md#L245-L266)).

## Borrow seven responsibilities, not either application’s stack

### Shared Rust use cases keep the browser honest

svrngs’ home join handler parses input and calls `at.host.join`; its CLI calls `node.host().join`. The routes also compose existing domain routers. This is actual peer access to shared behavior, not frontend reproduction of joining rules (svrngs `crates/svrngs-node/src/home.rs:156–164,652–668`; `crates/svrngs/src/cli.rs:1613–1638`). Canon already has a smaller version through `propose`, `replace`, and `review::decide`. Extend that seam into explicit queries/intents, with Rust returning eligibility, requirements, and outcomes. Cost is mainly separating ambient CLI resolution and terminal interaction from orchestration. An HTTP wrapper around CLI strings or generic arbitrary-act endpoint would preserve the wrong boundary.

### One object can hold several connected activities

The desktop client’s `NotebookDetail` uses one notebook identity for Ask, Explore, applicable Conflicts, Sources, and Settings; an explored subject or source question seeds scoped Ask. This implements a coherent object home (Commonwealth `clients/desktop/src/lib/components/library/NotebookDetail.svelte:122–184,416–440`). For canon, keep proposal, source, room, decision, and history connected within the selected record. The cost is navigation/return-state design, not a universal workbench framework. Desktop’s local tab state and hidden keep-alive chat do not supply browser bookmarks or reliable job lifetime; canon should use durable URLs and explicit state owners rather than copy those mechanics (same file, lines 509–521).

### Evidence should open at an address and admit mismatch

Desktop `openQuote` fetches stored text by its quote address and compares returned text with `quote.exact`; `TextSliceRenderer` shows source/range and a mismatch alert (Commonwealth `clients/desktop/src/lib/stores/readingSession.svelte.ts:343–366`; `clients/desktop/src/lib/components/reading/TextSliceRenderer.svelte:20–35`). Canon should distinguish saved quotation, recorded surrounding context, and current-file excerpt, with an unavailable/changed explanation and a return trail. Rendering saved draft evidence is relatively small; immutable addressing and portable storage are separately costed backend/privacy work. The desktop implementation is not uniformly race-safe: quote opens lack the identity guard used by `openAtom`, so borrow the evidence contract and add request-generation checks (`readingSession.svelte.ts:404–431`).

### State ownership follows the work’s lifetime

svrngs’ small pure-step/effect runner notifies state subscribers before launching effects; request counters reject late answers and group reads are independent. Desktop’s research store instead attaches to and recovers a backend job outside the originating view (svrngs `crates/svrngs-node/src/home/ui/machine.js:18–47`, `home/page/group.js:28–37`; Commonwealth `clients/desktop/src/lib/stores/deepResearch.svelte.ts:305–387`). Use local form state for ordinary writes and a record-bound recoverable owner for extraction/model work. Generation checks and explicit transitions are low-to-medium cost; durable jobs are additional scope. The svrngs runner has no cancellation/disposal API, and desktop’s store handles one active job. Neither justifies XState, a scheduler, or an event bus for normal append operations.

### A checked bridge needs accurate values and honest errors

Desktop centralizes invoke and generates command-name/argument-key maps with a drift test; its checked wrapper preserves error code and suggested action. However, values remain `unknown`, return types are caller assertions, and raw invokes still exist (Commonwealth `clients/desktop/src/lib/invoke.ts:10–42`; `clients/desktop/src-tauri/tests/command_surface.rs:180–251`; `clients/desktop/src/lib/api.ts:72–95,132–143`). For canon, one small checked adapter over a few actual use cases is preferable to a broad command mirror. Server validation and representative wire fixtures must cover field values, success variants, and failures; TypeScript assertions alone do not. Cost is modest for a bounded seam, materially larger for generation tooling. Do not import a 260-command bridge or treat incomplete typing as a proven end-to-end model.

### Pure semantic views make setup and accessibility reusable

svrngs shares native action/answer, labeled-field, and disclosure primitives; desktop separates setup event orchestration from a prop-driven screen that renders model provenance and failure/retry. Its shared dialog action implements focus entry, Tab containment, Escape, and restoration (svrngs `crates/svrngs-node/src/home/ui/parts.js:15–39`; Commonwealth `clients/desktop/src/lib/setup/SetupFlow.svelte:105–148`, `SetupScreen.svelte:65–112`; `clients/chat-ui/src/actions/dialog-focus.ts:46–114`). Reuse these responsibilities for canon’s context header, quotation, change preview, authority explanation, action result, and optional model setup/return. Shared native helpers are cheap; renderer adoption, fixtures, and focus behavior cost more. Avoid a design-system package, mandatory model downloads, or assuming reference controls already provide accessibility conformance; svrngs’ dynamic answer primitive has no live-region semantics.

### Tests and size accounting must cross the frontend boundary

svrngs tests failed effects, duplicate submission, invalid states, and late responses. Desktop continuity tests exercise leaving and returning to long work, while synthetic bridge tests deliberately exclude real-backend fidelity (svrngs `web/tests/machine.test.mjs:54–125`; Commonwealth `clients/desktop/tests/e2e/specs/deep-research-continuity.spec.ts:136–241`; `.github/workflows/ci.yml:304–338`). Borrow a few outcome/race/browser journeys, not their entire test apparatus. Also borrow their accounting cautions: svrngs prints an uncapped JS rung, and Commonwealth’s inspected Rust size collector does not count Svelte/TS/CSS (svrngs `scripts/lean_check.py:388–425,460–467`; Commonwealth `quality/xtask/src/size_gate.rs:429–441`). Large App/ChatView/API files are accumulated complexity, not recommended module sizes. Cross-boundary tests and a frontend inventory have moderate maintenance cost, which must accompany any claimed Rust savings.

### Repair incomplete truth before building new destinations

A supported revision check must cover the check-to-append interval across relevant writers; checking a hash immediately before an unlocked append does not remove the race. First report partial writes honestly using the current format. Then decide whether whole-operation serialization, multi-act submission, or an internal operation receipt is warranted, including signing/touch behavior and response-loss reconciliation. Changes to timestamps, act ordering, minted records, or admission semantics need explicit compatibility scrutiny, not a hidden “infrastructure” label.

Attention should name unverified acts, unattended rooms, ungoverned requests, dangling references, carried/uninterpreted annotations, and chronology problems where present, linking each qualification to evidence and a next step. These are not all proposals awaiting a vote; the existing terminal list/status already distinguishes much of this work ([list qualifications:797–858](../crates/canon-cli/src/cmds.rs#L797-L858); [status:16–65](../crates/canon-cli/src/status.rs#L16-L65)).

### One application seam can serve three adapters

Start with private modules inside `canon-cli`, extracting existing bodies only as another consumer needs them. The browser, CLI, and MCP should share typed application queries/use cases, **not the same transport**. MCP remains read-only. Keep transport parsing, authentication, CLI printing/prompts, and MCP envelopes in their adapters. Keep deterministic meaning in core and the selected institution reader; never reconstruct authority from browser roles or parse terminal prose to recover domain facts ([existing shared writes:318–331,544–699](../crates/canon-cli/src/cmds.rs#L544-L699); [ownership boundary:19–42,44–68](../docs/INSTITUTION_BOUNDARY.md#L19-L42)).

```text
Browser shell + feature pages ── checked HTTP/forms ─┐
CLI resolution / prompts / formatting ─────────────┼─ application use cases
MCP read adapters ─────────────────────────────────┘    context, queries, writes,
                                                       sources, model/run lifetime
                                                          │
                                        compatible reader + authoritative core
                                                          │
                                            immutable acts / local artifacts
```

An illustrative layout is small enough to evolve from today’s modules:

```text
canon-cli/src/app/{context,read,write}.rs   # explicit use cases, structured results
canon-cli/src/ui/{http,pages,parts}.rs     # gate; shell; shared native views
canon-cli/src/ui/{review,record}.rs        # cohesive journeys, not one file per verb
canon-cli/src/ui/assets/                  # only authored assets actually needed
draft.rs, review.rs, explain.rs           # reuse/extract bodies incrementally
```

This is a responsibility sketch, not a funded file split. A use case should load a consistent record snapshot with typed references, interpretation and clock policy, profile, freshness/revision, and diagnostics. A write takes a bounded intent and captured record/actor/target context; it returns recorded IDs, observed result, remaining requirements, and recovery information. Structured errors retain category, message, retryability, and observed write extent. A failed reread after append is an unknown outcome, not applied. HTTP status and HTML messages should reflect these distinctions without requiring a new public core API.

### Keep state, evidence, and long work with their owners

Rust owns signed history, interpretation, eligibility, source/run artifacts, model execution, and configuration policy. The shell owns resolved navigation/context; each feature owns unsent text, disclosure state, and its request generation. Server read snapshots can remain request-scoped. With progressive enhancement, retain a previous successful display only when visibly marked stale, refresh affected reads after mutations and tab return, and discard responses from earlier record/actor/interpretation generations. Historical and preview caches must be isolated from current work. Do not optimistically declare a governance result or erase typed work when external CLI/file changes arrive; MCP itself does not write.

Use ordinary request/response and POST/redirect/GET for short writes. Touch-required signing needs visible waiting and disconnect/uncertain-result handling, not automatic cancellation claims. Extraction, model checks, and conflict analysis justify longer-lived run state: record, actor, source selection, endpoint/model policy, phase, omissions, artifact identity, failure, and resume. Reuse draft checkpoints and resume/continue behavior before designing scheduling. Navigation can stop observing without stopping a run; stop-request acknowledgement and final outcome are distinct. No general platform, event bus, or ordinary-write background queue follows from this requirement ([saved runs:1719–1905,1999–2051](../crates/canon-cli/src/draft.rs#L1719-L1905)).

Source/history inspection should share stable record references and return paths. Display the saved quote/context separately from today’s file. Never silently replace missing original evidence with a similar passage. A future content digest or immutable source store must preserve signed source envelopes, and must decide what travels with a shared record: `.canon/seen` and draft runs are currently local, so sharing raw notes or rejection history cannot become an incidental export side effect ([saved-context validation:2350–2373](../crates/canon-cli/src/draft.rs#L2350-L2373); [ignored local state:151–187](../crates/canon-cli/src/store.rs#L151-L187)).

### Native HTML remains the best-supported starting point

Current forms, labels, disclosure, focus styling, system fonts, dark mode, and narrow-screen adjustments provide a useful baseline, not a completed accessibility audit. Server-rendered task pages can add search/filter, context, evidence, error preservation, and history without hydration. Their costs are server template complexity, explicit form round-tripping, and less convenient persistence across navigation. Small enhancement is justified for draft retention, request generations, or job-status refresh when a real journey needs it ([current HTML/CSS:1199–1308](../crates/canon-cli/src/ui.rs#L1199-L1308)).

svrngs proves modular frontend assets can be embedded in a Rust binary; its examined home uses vendored Preact/htm, whereas the desktop uses Svelte/TypeScript/Vite inside Tauri. Neither proves canon needs that renderer or delivery stack (svrngs `crates/svrngs-node/src/home.rs:90–164`, `home/ui/view.js:1–32`; Commonwealth `clients/desktop/package.json:2–16,42–72`, `clients/desktop/src-tauri/tauri.conf.json:6–61`). A compiled framework becomes a candidate if the source-review slice needs several coordinated retained panels and native-page enhancement produces duplicated state or inaccessible transitions. Compare the same slice’s authoring, tests, dependencies, embedded bytes, and cold readiness before choosing. Svelte’s compiled components could fit that stateful inspection work; Preact offers a smaller incremental component precedent. React has no specific advantage established by this evidence. No rewrite is selected now.

Preserve one production binary with build-time embedded, allowlisted assets and correct content types. If compilation is adopted, Node/Vite belong to development/release tooling, not the installed runtime. Release HTML, scripts, and styles as one coherent asset version, with no runtime CDN. Keep the security boundary explicit: loopback binding, exact Host, token bootstrap and HttpOnly/SameSite cookie, POST token/Origin/Fetch Metadata checks, escaping, no-store, and restrictive CSP. Adding scripts requires a narrowly reviewed same-origin script policy and browser tests, not broad `unsafe-inline` script permission. Signing remains server-side; key binding accepts offered fingerprints, not arbitrary paths, and HTTP exposes use-case intents, not arbitrary signed payloads ([security gates:214–230,290–390](../crates/canon-cli/src/ui.rs#L290-L390); [key gate:570–583](../crates/canon-cli/src/ui.rs#L570-L583)).

Likewise, source input needs a chosen access model—bounded uploads or explicitly approved local roots—not an arbitrary browser-supplied filesystem path or unrestricted URL fetch. Model setup reuses local-by-default endpoint gating and environment-secret handling, showing configured versus tested/failed/unchecked status, provider/model, observation time, and remote destination before text is sent. Manual work must remain usable without a model. Responsive layout should support narrow screens locally; access from a separate phone or a hosted multi-user service requires a distinct authentication/deployment decision, not changing the listener address ([model boundary:127–154,505–551](../crates/canon-cli/src/model.rs#L127-L154); [config/secrets:68–109,154–172](../crates/canon-cli/src/config.rs#L68-L109)).

Today’s excerpt boundary is the canonicalized record parent, not the original ingestion allowlist; for `~/.canon` that parent is the home directory. Preserve traversal protection while designing a narrower, explicit source capability rather than treating that existing boundary as a general-purpose file browser ([passage:276–298](../crates/canon-cli/src/review.rs#L276-L298)).

Increment 0 should preserve core public API, CLI output/flags, native minted records, existing MCP tools, and each surface’s legacy clock policy. Acceptance is a before/after inventory and representative equivalence checks over the same fixtures, with one consumer demonstrably using the extracted body. Do not broaden the seam into a universal application schema.

Increment 1 is the first product milestone. A participant in a governed fixture must find all pending proposal kinds, inspect the complete proposed wording and accurately labeled evidence, follow requirements to their record support, approve/object with a reason where required, and reach arbitrary-act history. A failed read must never say nothing needs attention or that a write applied. Validation failure retains wording/reason; injected second-append failure identifies the recorded portion; a stale decision is refused or explicitly reconfirmed against refreshed requirements under the supported writer model. Added POSTs retain token/origin refusal and leave the record untouched on rejected requests. These checks fund correctness of existing tasks before opening new ones. If the concurrency fix exceeds the envelope, re-cost it before claiming the milestone, rather than hiding the race behind a refreshed screen.

Increment 2 lets someone start without memorizing a CLI sequence: choose open versus create deliberately, see record/profile/founding authority, identify, read people/procedures, find a question/due item, manually propose with source/reason, and recover pending work or a prior act through permitted cancellation/undo. Private check and public question must produce observably different storage effects. Add optional model configuration and read-only MCP setup with a return to the initiating task; do not require a model to read, decide, or author manually. Multi-record sessions require real-browser isolation tests first. A launcher that removes the initial terminal step remains a separate packaging decision.

Increment 3 completes discovery: choose bounded sources, show skipped/capped/unread counts and model destination, leave/reopen a run, inspect exact saved evidence, accept/edit/reject/skip individually, and resume without repeating extraction. Source reading can fail while preserving artifact and input; remote text transfer requires explicit permission in captured job context. Immutable evidence portability is a separately priced design if current local artifacts are insufficient.

Increment 4a exposes seat terms/expiry, room claims, procedure/ruling changes, and positions with readable authority before editing. Its separately accepted resource slice uses one existing fixture to show a turn, allocate through existing rules, and finish announce/seal/open/show with draw secrets kept local. Questions, conflict decisions, revisit dates, and operational decisions must lead back to supporting evidence and required people. Increment 4b starts with export and read-only snapshot/lineage/policy comparison: source bytes remain unchanged, a counterpart parses the snapshot, upstream/local IDs remain connected, and existing replay preview never invokes materializing `--out`. Rebase, adoption, and upgrade writes need their own authority, model, and partial-failure acceptance before being enabled.

A fork/adopt journey should name the originating record, the new local copy, inherited IDs, and the difference between accepting an upstream change and making a local one. Preview what travels—including evidence—and what remains machine-local. Record portability is not a promise of live collaborative editing or automatic reconciliation of divergent copies.

Increment 5 initially compares the six-date institution-house example under explicitly retained arrangements: identical source/arrangements fingerprints and effective times, separate admissions and pending display, unsupported inputs refused, neither input modified, and ordinary UI/CLI/MCP unchanged. **Institutional adoption is not included in that estimate.** It requires the versioned product/interpretation decision described above. Private browser endpoints and new HTML can preserve existing public contracts, but changing common CLI errors/output, minted act ordering/timestamps, core APIs, or interpretation can move them. Inspect failing contract diffs and obtain operator approval before any blessing; record reinterpretation also needs migration/reinterpretation tests and a “Before you upgrade” changelog entry ([working rules:8–21](../CLAUDE.md#L8-L21)).

### Success is task completion and clear evidence, not more controls

For the first milestone, propose a small observed study with five participants across the relevant profiles: at least four complete the decision→outcome→history task without terminal assistance, and all correctly identify record, actor, evidence availability, and whether the change is pending or effective. This is a proposed threshold, not a statistical claim or measured baseline. Record where they hesitate and why. Measure task completion/time, incorrect authority assumptions, preserved input after errors, and successful reconciliation after an uncertain response. Benchmark small and import-heavy fixture records before setting a latency target; the current queue clones/rederives per pending item and no measured responsiveness bound exists ([queue cost:221–258](../crates/canon-cli/src/review.rs#L221-L258)).

Attach checks to responsibility boundaries. Rust fixtures remain the semantic oracle; application tests cover clock/context, refusal, partial writes, and recovery. Transport tests exercise real disposable records, signing, POST gates, malformed framing, and history resolution. Small synthetic browser tests cover late responses and failures; real-server journeys verify that UI actions append the expected acts. Keyboard-only completion must include source/history return, visible focus, labels and status/error announcements; narrow-screen tests at 320px and 200% text must keep controls and evidence readable. Measure light/dark contrast and test screen-reader behavior for critical feedback. Remote phone reachability is not part of this responsive check.

A clock acceptance case should cross a consent deadline or seat expiry without appending anything, then verify that state, requirements, and explanation agree with the chosen view clock. Pin the existing MCP clock policy separately rather than making equivalence tests silently normalize it.

## Conclusion

The immediate decisions are concrete: choose local-browser single-binary delivery for this phase; select the existing-record participant loop as the first milestone; fund a narrow shared-use-case extraction and truthful failure model; require whole-frontend accounting alongside Rust; and retain legacy interpretation while treating any institutional preview/adoption as separate, versioned work. Defer renderer selection until the notes-to-proposal slice provides a meaningful comparison. These choices give canon room to become a complete product without making its browser a second governance engine.

The realistically small starting slice is **working history and honest attention/outcomes for one governed record**, including a pending policy decision, a refusal/read failure, and preserved input. Review its actual diff and cost before expanding to first-run and recovery, then source discovery and stewardship. A UI earns first-class status when someone can finish their next consequential task and explain what the record now means. This report approves no app implementation; it supplies the bounded decisions and evidence needed to approve one.
